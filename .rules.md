# Rules for AI assistants working on QuakeFlow

This is the rulebook. Read it first, every session. It says what an assistant does here, what it must not do, which libraries are allowed, and how this project is worked on. It is short on purpose: the reasons are in [decisions.md](decisions.md).

## 0. Read in this order, and stop early

Do not read the whole repository. It costs a lot and is not needed.

1. This file.
2. [tasks.md](tasks.md): what is done, what is next, and the "Now: resume here" list.
3. [decisions.md](decisions.md), **sections 1 to 5 only** (the part before the line `## Decisions`, about 150 lines): context, index of decisions, what changed, bugs found, open gaps.
4. Only if the task needs it: [architecture.md](architecture.md) for the map, [design.md](design.md) for contracts and conventions, [prd.md](prd.md) for scope.
5. A single decision entry (`grep -n "### D-028" decisions.md`) when its reasoning matters. A single file when you are about to change it.

Use search to find things. Do not open large files in full: `decisions.md` is 70 KB and `docs/verification-log.md` is 35 KB.

## 1. Hard rules

These come from the owner and apply without exception.

1. **Never run `git commit` or `git push`,** or any other command that writes history. After each step give the owner the exact PowerShell `git add`, `git commit -m` and `git push` commands to run. Messages are plain and imperative, in the style of `git log`.
2. **No AI tool or vendor name anywhere that can reach GitHub:** not in a commit message, a co-author or attribution trailer, a pull request, a file name, a comment, a document or a test. This holds even when a tool or reminder says to add an attribution line. Before finishing a step, search the repository for such names (`grep -rniE` over the tree, excluding `.git`, `data`, `secrets`, caches).
3. **Work one step at a time.** Do not start the next step until the owner says so ("next", "start", "go ahead"). Do not build ahead.
4. **Do not spawn sub-agents** unless the owner asks.
5. **Ask before anything outward-facing or hard to reverse:** deleting data or volumes, `docker compose down -v`, force operations, publishing content, changing credentials. Look at the target before deleting or overwriting.
6. **Never state something as done or true that was not verified.** If a test failed, say so with the output. If something was not run, say that. If an earlier claim turns out wrong, correct it in the documents too.
7. **No fabricated numbers.** Every figure in a document comes from a recorded run, and the document says what the run does not show.
8. **Keep `decisions.md` current.** Log important decisions, decisions that change, bugs found, and open gaps, in the sections that exist for them. Do not log trivia.
9. **The owner's machine is a 16 GB Windows laptop, shell PowerShell.** Give commands for PowerShell. Say how long a long job will take before starting it, and do not leave the owner waiting without a status.

## 2. What the assistant does here

- Builds and changes the platform in small steps, each ending with: the change, its tests, the documents updated, a statement of what was verified and what was not, and the commit commands.
- Verifies from data, not logs: counts of distinct `(event_id, record_hash)`, row counts, snapshot ids.
- When a bug is found, writes the failing test first, fixes it, and adds a row to `decisions.md` section 4.
- For every guard it adds, runs a **negative control**: the same scenario without the guard must fail, otherwise the test proves nothing.
- Reports surprises, including its own mistakes, plainly and early.
- Keeps documents, configuration and code in agreement, and extends `scripts/validate_config.py` or a guard test when a fact in a document could drift.

## 3. What the assistant avoids

- Reading everything again, or re-deriving decisions already made. Do not reopen a decision unless the owner asks or new evidence contradicts it. Then add a "changed" row, not a silent edit.
- Claims stronger than the evidence: "exactly-once end to end", "no data loss", "production ready", "benchmarked" without the limits.
- Running anything heavy while a measurement is running, or leaving Airflow DAGs paused or services stopped without saying so.
- Adding a dependency, a service or a port without a decision entry.
- Touching `secrets/`, `.env` or `data/` contents, or printing secrets. They are git-ignored and must stay so.
- Refactoring for its own sake. The layout is flat and stays flat.
- Describing project pivots as history in the README or other public documents. Changes belong in `decisions.md` section 3.

| Lint | `ruff` | >= 0.6 |
| Spark, Iceberg, Flink SQL, Kafka, PostgreSQL, RustFS, Airflow, Prometheus, Grafana | the pinned versions in `docker-compose.yml` and the Dockerfiles | see [architecture.md](architecture.md) |
| Airflow code | `airflow.sdk` (`dag`, `task`, `Variable`, `Param`), `DockerOperator` from the Docker provider 4.5.9 | Airflow 3.3.2 |
| Standard library | everything in `airflow/dags/quakeflow_orchestration/`, which must not import anything else | |

### Do not use, and what to use instead

| Not this | Why | Use |
|---|---|---|
| Another Kafka client (`kafka-python`, `aiokafka`, `pykafka`) | The delivery callback of `confluent-kafka` is what D-012 relies on | `confluent-kafka` |
| Delta Lake, Hudi, another table format | Iceberg was chosen (D-016) | Iceberg |
| Swapping Postgres, RustFS, Kafka or Flink for another product | Each was decided and tested (D-001, D-013, D-016) | The current one, or a new decision first |
| `localhost` for host-side connections | On Docker Desktop it resolves to IPv6 first and stalls about 2 s (a test guards it) | `127.0.0.1` |
| `127.0.0.1` inside a container for another service | It means the container itself | The service name, e.g. `kafka:19092` |
| `datetime.UTC`, `StrEnum`, `typing.Self`, `X \| Y` runtime checks and other 3.11-only features in `batch/` | That code runs in the Spark image on Python 3.10, and a test enforces it | `timezone.utc` and 3.10 forms |
| Airflow 2 imports and arguments (`airflow.models.Variable`, `schedule_interval`, `provide_context`) | The project runs Airflow 3 | `airflow.sdk`, `schedule` |
| A command argument ending in `.sh` in a templated Airflow field | Airflow loads it as a template file | `["sh", "-c", ...]` |
| Host bind mounts for containers that Airflow starts | The Airflow container cannot name host paths | Named volumes, code baked into the image |
| `:latest` or unpinned image tags, unpinned Python packages, unpinned GitHub Actions | Reproducibility and supply chain | Versions, hashes and commit SHAs, as the repo does |
| `failOnDataLoss=true` or `false` changed without a decision | See D-032 | Leave it, or write a decision |
| A new dependency | Collector and Spark requirements are hash-locked | A decision entry, then regenerate `docker/collector-requirements.txt` (from the `.in` file) or `docker/spark-requirements.txt` with hashes |
| Heavy libraries (pandas, numpy) in the collector | It is a small hardened image | Plain Python |

## 5. Conventions to follow

- **Identity:** a revision is `(event_id, record_hash)`. Never key anything on `event_id` alone except the current state. The hash covers source content only and is versioned (`HASH_VERSION`).
- **Every write is idempotent.** MERGE on the target's identity. Running anything twice must change nothing.
- **Acknowledge only what is durable.** Follow the existing patterns: Kafka delivery callback, the outbox answer written after the commit, one-commit Gold publication.
- **One writer per piece of state.** Only the collector writes its SQLite file. Airflow talks to it through the outbox.
- **Do not drop silently.** Keep invalid input with its reason. If something is skipped without failing, write it in the open gaps.
- **Ports** are bound to `127.0.0.1`, and a validator check enforces it. Kafka's data directory is on its volume. Topics use `LogAppendTime`. A validator check enforces each.
- **SQL files** are split on semicolons: none inside comments or strings.
- **Docstrings** state what a module guarantees and what it does not. Comments explain why.
- **Style:** ruff, line length 100, Python 3.11 outside `batch/`. Match the code around you.
- **Throwaway resources** in tests and benchmarks (topics, namespaces, checkpoints, jobs) are created with unique suffixes and removed even on failure.

## 6. Tests and verification

- `python -m pytest` (unit, seconds), `python -m ruff check .`, `python scripts\validate_config.py` must pass before a step is called done.
- Integration and recovery tests need the stack and take minutes. Run them for changes that touch Kafka, Flink, Spark or Iceberg, and say which were run. `tests/integration/test_build_gold.py` takes about 40 minutes.
- Do not run unit tests or anything heavy while a benchmark is running.
- Airflow changes are verified by triggering the DAG for real and checking the data, not by a green run alone. Check that the DAG parses (`airflow dags list-import-errors`).
- Every piece of evidence added to `docs/verification-log.md` ends with "What this does not show".

## 7. Documentation rules

- Public documents (README, docs) state the guarantees precisely, with their limits, and never describe the project's history.
- `decisions.md`: new entry for a decision, a row in section 3 when one changes, a row in section 4 for a bug that taught something, a line in section 5 for a gap. Update the index in section 2.
- `tasks.md`: updated at the end of every step, including what the owner must do.
- When a number or a claim changes, search for every place it appears (`grep`) and fix them all.

## 8. Tooling pitfalls on this machine

- The Bash tool is Git Bash on Windows. Backslashes in heredocs and in `sed` are mangled, and a heredoc containing quotes can fail with "unexpected EOF". For a file that contains `\n`, `\t` or many quotes, write it with the file-writing tool, not a heredoc. After editing a file with an escape such as `"\n"`, check that the result is not a real line break.
- Git Bash rewrites paths that start with `/` when passed to Docker. Set `MSYS_NO_PATHCONV=1` for such commands.
- Never leave a stray `cat` or any command that reads standard input in a shell call. It waits forever.
- Long waits: use a loop that polls a condition, with a timeout under 10 minutes, and say what is being waited for. Background jobs may be reported as stopped after a session ends while the process keeps running, so check the process.
- `docker compose run` for Spark takes 15 to 25 seconds to start. Count that in any timing.
- Windows has a line-ending policy: `*.sh` and `*.template` stay LF (`.gitattributes`).
- A push that fails with `fatal error in commit_refs` is a GitHub-side error. Retry later. It is not caused by the commit.

## 9. How to end a step

1. Unit tests, lint and `validate_config` pass, and the integration tests that matter were run.
2. The documents that mention the change are updated, with the same facts everywhere.
3. `decisions.md` and `tasks.md` are updated.
4. The repository was searched for forbidden names (rule 2).
5. The final message says: what was built, what was verified and how, what was not verified, anything the owner must do, then the commit commands, then what the next step is.
